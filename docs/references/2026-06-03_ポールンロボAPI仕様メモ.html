1. エンドポイントとパラメータ

GET https://wxtech.weathernews.com/opendata/v1/pollen
  ?citycode=<市区町村コード>     例: 27123
  &start=<開始日 yyyyMMdd>      例: 20260301
  • レスポンス：CSV（text）。Content-Type はテキスト。JSONではない。
  • 1行目はヘッダ行：citycode,date,pollen
  • 2行目以降が1時間ごとのデータ（00:00, 01:00, 02:00 …）

2. CSV列構成 ↔ ユビキタス言語 ↔ Entity/DTO

CSV列ユビキタス言語
(CLAUDE.md用語集)		意味Entity フィールドDTO フィールドDB列
citycode 観測地点
(Observation Point) の識別子		 市区町村単位の観測ポイントを表すコード ObservationPoint.externalId cityCode observation_points.external_id
date 花粉観測値
(Pollen Measurement) の観測時刻		 その飛散数を観測した日時（1時間刻み） PollenMeasurement.measuredAt measuredAt pollen_measurements.measured_at
pollen 花粉観測値
(Pollen Measurement) の飛散数		 花粉飛散数（個/m³） PollenMeasurement.pollenCount pollenCount pollen_measurements.pollen_count
🟢 重要な対応：CSVには citycode しか地点情報が無い。これが ObservationPoint.externalId に一致する。だから取り込み時は observationPointRepository.findByExternalId(citycode) で地点を解決する（無ければ新規作成）。
そして1行（citycode + date + pollen）が 1個の PollenMeasurement に対応する。

3. date の形式（重要：+09:00付き）

2026-03-01T00:00:00+09:00
🟢 ISO 8601 形式で、末尾に タイムゾーンオフセット +09:00（日本時間, JST）が含まれている。
→ 自分でJSTと推測する必要がなく、そのまま Instant(UTC基準) に変換できる： 
Instant measuredAt = OffsetDateTime.parse("2026-03-01T00:00:00+09:00").toInstant();
// 結果: 2026-02-28T15:00:00Z （UTCに正しく変換される）
🟣 application.yml の hibernate.jdbc.time_zone: UTC と整合。DBには TIMESTAMPTZ でUTC基準保存され、表示時にタイムゾーン変換できる。

4. pollen の意味（0 と 欠測 の違い）

値意味扱い
0観測できた・花粉ゼロ（飛散なし）✅ 正常値。保存する
1 以上飛散数（個/m³）✅ 正常値。保存する
-9999 など負数欠測（観測なし・センサー停止）❌ スキップ（保存しない）
🔴 最重要の誤解ポイント：0 を「データ無し」と誤解して捨てない。0 は「観測した結果ゼロ」という正常データ。捨てるべきは負数（欠測）だけ。
🟢 欠測値は -9999 と確認済み（2026-10-05、citycode=27123, start=20260820 で実機確認。24時間すべて -9999 の日があった → 下記例C）。それでもコードでは「pollen < 0 なら欠測としてスキップ」という防御的な実装を変える必要はない（-9999以外の負数が来ても一律に弾けるため、より安全）。PollenMeasurement.of() の負数ガードが最後の砦。

5. 実レスポンス例

例A：3月（花粉シーズン・飛散あり）

citycode=27123 / start=20260301 / 2026-06-03 取得
citycode,date,pollen
27123,2026-03-01T00:00:00+09:00,0
27123,2026-03-01T01:00:00+09:00,0
27123,2026-03-01T02:00:00+09:00,1
27123,2026-03-01T03:00:00+09:00,1
27123,2026-03-01T04:00:00+09:00,1
...

→ 深夜は0、明け方から 1 が出始める。0と正の値が混在＝これが通常パターン。欠測（負数）は無い。

例B：6月（オフシーズン・全ゼロ）

citycode=27123 / start=20260603 / 2026-06-03 取得
citycode,date,pollen
27123,2026-06-03T00:00:00+09:00,0
27123,2026-06-03T01:00:00+09:00,0
27123,2026-06-03T02:00:00+09:00,0
27123,2026-06-03T03:00:00+09:00,0
27123,2026-06-03T04:00:00+09:00,0
...

→ オフシーズンは終日 0。これも正常データ（保存対象）。欠測ではない。

例C：8月下旬（観測終了間際・欠測）

citycode=27123 / start=20260820 / 2026-10-05 取得
citycode,date,pollen
27123,2026-08-20T00:00:00+09:00,-9999
27123,2026-08-20T01:00:00+09:00,-9999
27123,2026-08-20T02:00:00+09:00,-9999
...（24時間すべて -9999）

→ 0と違い、終日 -9999 になる日がある＝これが欠測。pollen < 0 のガードで正しくスキップされる。

🟣 citycode 27123 = 大阪市某区（27=大阪府）。地点名（ObservationPoint.name）はAPIに含まれないため、別途自分で付ける必要がある（要検討：論点として下記）。

6. 観測期間外のレスポンス（404 / 400）

🔴 観測期間を過ぎると、CSVそのものが返らず404になる（0埋め・欠測埋めのCSVではない）。PollenApiClient.fetchRawCsv() はこの404をハンドリングしていないため、HttpClientErrorException$NotFound がそのまま例外として伝播する。

2026-10-05 に citycode=27123 で、start を1日ずつ変えて実機確認した結果：

startHTTPステータス内容
〜 2026-08-24200CSVが返る（花粉0、または欠測 -9999 が混在。例A〜C）
2026-08-25 〜 今日404{"errors":[{"message":"data does not exist"}]}
観測そのものが行われていない期間。CSVは1行も返らない
今日より後の未来日400{"errors":[{"message":"start must be less than or equal today"}, ...]}
未来日を指定した場合のバリデーションエラー（404とは別のエラー）
🟡 この境界日（2026-08-24）は citycode=27123 固有の値で、花粉の種類・地域によって観測期間は異なると考えられる（スギ花粉は春、ブタクサなど秋の花粉もあるため、地点や品種設定によって期間がズレる可能性がある。未確認）。「○月×日を過ぎたら必ず404」という決め打ちはできない。
🔵 実装への影響：IngestRunner が LocalDate.now() を使う本番運用では、観測期間外の時期は毎回404で例外が発生する。これは「バグ」ではなく「データが無い」という正常な状態なので、将来的には PollenApiClient 側で404を捕捉し「データ無し」として扱う（例外を投げずに空リストを返す、など）設計が必要になる。Phase 1の時点では、動作確認用に観測期間内の日付（例：2026-03-01）を一時的に指定して検証している。

7. 変換の流れ（CSV1行 → PollenMeasurement）

"27123,2026-03-01T02:00:00+09:00,1"
        │
        ├─ citycode "27123"  → findByExternalId("27123") で ObservationPoint を解決
        ├─ date     "...+09:00" → OffsetDateTime.parse(...).toInstant()  → measuredAt
        └─ pollen   "1"         → Integer.parseInt → pollenCount
        │
        ▼ pollen が負数なら ここでスキップ（欠測）
   PollenMeasurement.of(point, measuredAt, pollenCount)
        │
        ▼ existsByObservationPointAndMeasuredAt で重複チェック後
   repository.save(...)
