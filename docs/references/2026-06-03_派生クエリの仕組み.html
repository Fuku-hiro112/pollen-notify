🧬 派生クエリ：メソッド名がそのままSQLになる仕組み

花粉通知アプリ ／ 2026-06-03 ／ Phase 1 ／ Spring Data JPA の核心

🔑 この資料の核心（一文で）
Spring Data JPA には「findByExternalId という既製の関数」は存在しない。あなたが書いたメソッド名という文字列を、Springが起動時に解析し、その場でクエリを組み立てる。つまり メソッド名は「呼び出す関数の名前」ではなく「クエリの設計図（DSL）」である。
🟢 これがなぜ革新的か：普通のプログラミングでは「実装を書く」。だが派生クエリでは 「何が欲しいか（意図）」を名前で宣言するだけで、実装（SQL）は自動で導出される。命令型ではなく宣言型。SQLの定型作業を人間から機械へ移した発明。

1. よくある誤解 → 正しい理解

❌ よくある誤解✅ 正しい理解
findBy とは「findBy用の関数」が用意されていて、それが割り当てられる関数は無い。findBy は「SELECTして返せ」という指示キーワード
メソッド名とは呼び出す関数の名前クエリの設計図（文字列で書いたDSL）
誰が実装を持つJpaRepositoryのどこかにある誰も持たない。名前から起動時に生成される
気をつけること（なんとなく命名規約）名前が仕様そのもの。1文字ズレれば違うクエリ／起動失敗
🟡 save() や findById() は事情が違う：これらは SimpleJpaRepository という本物の既製実装がある（＝あなたの最初の認識どおり）。派生クエリ（findByXxx）だけが「名前から生成」。この2種類を区別するのが理解の鍵。

2. メソッド名の解剖（主部 + 述部）

派生クエリのメソッド名は、英文のように 主部（Subject） と 述部（Predicate） に分かれます。境界は By。

  • 主部：exists / find / count など。操作の種類と戻り値の型を決める。
  • By：ここから条件が始まる、という区切り。
  • プロパティ：Entityのフィールド名（camelCase）。WHEREの対象列になる。
  • 演算子（任意）：LessThan Like など。省略時は =。
  • 連結：And / Or。

3. 主部キーワード（操作と戻り値を決める）

existsBy条件に合う行が存在するかboolean

プロパティ名のうしろに演算子を続けると、= 以外の条件になります（演算子省略時は =）。

5. 本プロジェクトの2例を完全分解

例1：findByExternalId(String externalId)

find        → SELECT して取得（戻り値は Optional<ObservationPoint> と宣言）
By          → ここから条件
ExternalId  → Entityのフィールド externalId（DB列 external_id）を = で照合
↓ Spring が起動時に生成（JPQL）
SELECT o FROM ObservationPoint o WHERE o.externalId = :externalId
↓ Hibernate が変換（実SQL / PostgreSQL）
SELECT ... FROM observation_points WHERE external_id = ?

例2：existsByObservationPointAndMeasuredAt(ObservationPoint p, Instant at)

exists            → 存在するか（戻り値 boolean）
By                → 条件開始
ObservationPoint  → フィールド observationPoint（FK observation_point_id）を = 照合
And               → かつ
MeasuredAt        → フィールド measuredAt（列 measured_at）を = 照合
↓ JPQL
SELECT count(m)>0 FROM PollenMeasurement m
WHERE m.observationPoint = :p AND m.measuredAt = :at
↓ 実SQL
SELECT EXISTS(SELECT 1 FROM pollen_measurements
              WHERE observation_point_id = ? AND measured_at = ?)
🟢 引数 p（ObservationPoint）を渡すと、Hibernateがその id を取り出して observation_point_id = ? に当てる。オブジェクトのままFK条件にできるのがJPAの便利な点。

6. 戻り値の型のルール

主部使える戻り値の型使い分け
findBy（1件想定）Optional<T>「無いかも」を型で表す。推奨。本プロジェクトの findByExternalId はこれ
findBy（1件想定）T（生の型）無いと null。null安全でないので避けたい
findBy（複数）List<T>0件は空リスト。複数ヒット前提
existsByboolean存在チェック専用。重複防止に最適
countBylong件数
🔴 1件想定で ListでなくT/Optionalを使う場合、結果が2件以上あると例外（IncorrectResultSizeDataAccessException）。findByExternalId が Optional で安全なのは、external_id に UNIQUE制約があり「最大1件」が保証されているから。型の選択はDB制約と整合している必要がある。

7. プロパティの掘り下げ（関連のたどり方）

条件は、関連先のフィールドまでたどれます。例えば「external_id が一致する観測値」を測定値側から引きたい場合：

// PollenMeasurement から ObservationPoint.externalId をたどる
List<PollenMeasurement> findByObservationPointExternalId(String externalId);
//                              └────┬────────┘└───┬────┘
//                          observationPoint  .externalId （関連を辿る）
🟡 たどり先が曖昧な場合（例：observationPointExternalId が observationPoint.externalId か observationPointExternal.id か紛らわしい時）、アンダースコアで明示できる：findByObservationPoint_ExternalId。普段は不要だが、解決エラーが出たら使う。

8. Springはどう解析しているか（PartTree）

  1. 起動時、PartTree がメソッド名を主部・述部に分解
  2. 述部のトークン（ObservationPoint, MeasuredAt…）を、Entityのフィールド名と突き合わせて解決
  3. 解決できたらJPQLを組み立て、メタデータとして保持
  4. 実行時：保持したJPQLに引数をバインドして実行 → Hibernateが実SQLへ
🔴 ステップ2でフィールド名に解決できないと起動失敗：
PropertyReferenceException: No property 'cityName' found for type 'ObservationPoint'
タイポ（findByExternalIdd）や存在しないフィールド（findByCityName）はアプリ起動の瞬間に発覚する。実行を待たない（fail-fast）。

9. 派生クエリの限界と @Query への切り替え

名前で書けるのは「単純〜中程度」まで。複雑になると名前が長大化し、むしろ読めなくなります。

状況手段
単純な条件（=, And, 範囲, 並べ替え）✅ 派生クエリ（メソッド名）
名前が findByAAndBAndCOrderByDDescAndEAsc... と暴走⚠️ @Query でJPQLを直接書く方が読みやすい
集計・サブクエリ・JOIN FETCH・DB固有関数✅ @Query（JPQL / nativeQuery）
🔵 @Query の例（Phase 3以降で登場） 
@Query("SELECT m FROM PollenMeasurement m " +
       "WHERE m.observationPoint = :p ORDER BY m.measuredAt DESC")
List<PollenMeasurement> findRecent(@Param("p") ObservationPoint p, Pageable pageable);
🟣 Phase 1は派生クエリで十分。「名前が長すぎてつらい」と感じたら @Query への切り替えサインだと覚えておく。

10. 理解度チェック

Q1. 「findBy用の関数が割り当てられる」という説明はどこが間違い？

既製の関数は存在しない。findBy は「SELECTして返せ」という指示キーワードで、メソッド名全体を解析してクエリが生成される。名前は関数名ではなくクエリの設計図。

Q2. save() と findByExternalId() で、実装の出どころはどう違う？

save()＝SimpleJpaRepository という既製実装。findByExternalId()＝メソッド名から起動時に生成。前者は「ある関数」、後者は「名前から作られる」。

Q3. findByExternalId の戻り値を Optional にできるのはなぜ？ もし name で同じことをしたら？

external_id はUNIQUEなので最大1件＝Optionalで安全。name はUNIQUEでないため複数ヒットしうる→ Optional/T だと例外。List にすべき。型はDB制約と整合させる。

Q4. findByPollenCountGreaterThanAndMeasuredAtAfter は引数が何個必要？

2個。GreaterThan(1個) + After(1個)。順番は名前に出る順＝(count, instant)。

Q5. メソッド名にタイポした場合、いつ・どんなエラーで気づく？

アプリ起動時に PropertyReferenceException。フィールド名に解決できないため。実行を待たず即発覚（fail-fast）。

11. 次にやること

🟢 この仕組みが腑に落ちたら、外部API連携（ガイド）で findByExternalId（地点解決）と existsByObservationPointAndMeasuredAt（重複防止）が実際に動くのを確認できます。show-sql: true のログで、あなたのメソッド名がどんなSQLになったかを自分の目で観察すると、この資料の内容が一気に実感に変わります。
🟣 Phase 4への伏線：派生クエリは「永続化の関心事をRepositoryに閉じ込める」DDDの考え方と相性が良い。ドメイン層は「findByExternalId という意図」だけ知り、SQLという実装詳細を一切知らずに済む。これがリポジトリパターンの理想形。
