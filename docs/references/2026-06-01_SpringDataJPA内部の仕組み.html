1. 結論：実装ファイルは存在しない

あなたがプロジェクト内をいくら探しても、ObservationPointRepositoryImpl.java のような実装クラスは見つかりません。自動生成された .java ファイルすら作られません。実装は実行時（アプリ起動時）にJVMのメモリ上で組み立てられるからです。

🔵 一言でいうと：あなたが書いた interface を実装した「プロキシオブジェクト」を、Springが起動時に動的に作り、Beanとして登録する。

2. 起動時に何が起きているか（ブートストラップ）

Spring Boot を使っていると @EnableJpaRepositories を自分で書く必要すらありません（自動構成 / Auto Configurationが裏で有効化）。だから「ただ interface を置くだけ」で動くのです。

3. プロキシとは何か（動的プロキシ）

🟢 プロキシ（proxy）= 代理人。本物の代わりに呼び出しを受け取り、必要な処理を挟んでから本体に渡すオブジェクト。Spring Data JPA は、あなたの interface を実装した代理人を実行時に生成します。

技術的には JDK動的プロキシ（Dynamic Proxy）が使われます。interface に対して「呼び出しを横取りする1つの窓口（InvocationHandler）」を仕込み、どのメソッドが呼ばれたかを見て処理を振り分けます。

// あなたが受け取るのは interface 型だが…
ObservationPointRepository repo;   // ← 中身は Springが作った代理人

repo.getClass();  // 実行時に確認すると → "jdk.proxy3.$Proxy123" のような名前
                  //   = ディスクに無い、実行時生成クラスの証拠

4. 2種類のメソッドの実装の出どころ

プロキシは、呼ばれたメソッドを2種類に振り分けます。

種類例実装の出どころ
標準CRUDsave findById findAll countSpring Data JPA同梱の実クラス SimpleJpaRepository に委譲。内部で EntityManager を呼ぶ。
派生クエリfindByExternalId existsByObservationPointAndMeasuredAtメソッド名を起動時に解析して生成したクエリ実行ロジック（QueryExecutorMethodInterceptor が担当）。
@Query 指定@Query("...") 付きメソッドあなたが書いたJPQL/SQLを実行（Phase 3以降）。
🟣 SimpleJpaRepository が「本物の実装」。プロキシはその前に立つ受付係で、標準メソッドはそこへ取り次ぐ。つまり「全く実装が無い」のではなく、「共通実装＋メソッド名からの生成」を組み合わせている。

5. 派生クエリはどう解析されるか（PartTree）

ここが「メソッド名を書くだけ」の正体です。Spring Data は PartTree という解析器でメソッド名をトークンに分解します。

existsByObservationPointAndMeasuredAt
 │     │               │   │
 │     │               │   └─ MeasuredAt … プロパティ measuredAt の条件
 │     │               └───── And ……… AND で連結
 │     └───────────────────── ObservationPoint … プロパティ observationPoint の条件
 └─────────────────────────── existsBy …… 「存在するか(boolean)を返す」

これを元に JPQL（≒オブジェクト指向のSQL）を組み立て、最終的に Hibernate が実DBの SQL へ変換します。

existsByObservationPointAndMeasuredAt(point, at)
   ↓ Spring Data が生成（JPQL）
SELECT ... WHERE m.observationPoint = :p AND m.measuredAt = :at
   ↓ Hibernate が変換（実SQL / PostgreSQL）
SELECT ... WHERE observation_point_id = ? AND measured_at = ?
🟡 解析対象はEntityのフィールド名(camelCase)。ObservationPoint や MeasuredAt はフィールド observationPoint / measuredAt に対応する。DB列名(snake_case)ではない点に注意（命名規則リファレンス参照）。
📚 公式：Query Methods ／ Query Keywords Reference

6. トランザクションは誰が張るか

🟢 SimpleJpaRepository の各メソッドには @Transactional が付いています。だから save() 1回はそれだけでトランザクションになります（=プロキシがDB接続の開始/コミット/ロールバックを面倒みる）。

ただし「複数の保存をまとめて1トランザクションにしたい」場合は、呼び出す側（Service）に @Transactional を付けて束ねます。これは次のステップで効いてきます（複数観測値の一括保存など）。

7. なぜ起動時にエラーで落ちるのか

派生クエリの解析は起動時（プロキシ生成時）に行われます。だからメソッド名のミスは実行を待たずに発覚します。

🔴 例：タイポや存在しないフィールド
findByExternalIdd(...) や findByCityName(...)（cityName フィールドが無い）と書くと——
PropertyReferenceException: No property 'xxx' found for type 'ObservationPoint'
というエラーでアプリが起動しない。
🟣 これは利点。実行してその行に到達するまで気づけない…のではなく、起動直後（=開発中すぐ）に気づける。fail-fast の好例。

🟡 show-sql は学習中はON推奨。ただし本番は大量ログになるのでOFF。Phase 1の今は「自分のメソッド名がどんなSQLになるか」を観察する絶好の機会。

9. もしSpring Data JPAが無かったら

ありがたみを知るため、同じことを素のJPA（EntityManager）で書くとどうなるか：

// findByExternalId 相当を手書きすると…
public Optional<ObservationPoint> findByExternalId(String externalId) {
    String jpql = "SELECT o FROM ObservationPoint o WHERE o.externalId = :eid";
    List<ObservationPoint> result = entityManager
            .createQuery(jpql, ObservationPoint.class)
            .setParameter("eid", externalId)
            .getResultList();
    return result.stream().findFirst();
}

これを全メソッド・全Entityで書くのは退屈でバグの温床。Spring Data は「メソッド名という宣言」だけでこれを肩代わりしている、というわけです。「単純で機械的なものは機械に任せ、人は意図の宣言に集中する」思想。

10. 理解度チェック

Q1. findByExternalId の実装は、プロジェクトのどのファイルにある？

どのファイルにも無い。アプリ起動時にSpringがプロキシとしてメモリ上に生成する。

Q2. save() の実装の「本体」はどこにある？

Spring Data JPA同梱の SimpleJpaRepository。プロキシは標準メソッドをそこへ委譲する。

Q3. メソッド名を findByCtyName とタイポした。いつエラーになる？

アプリ起動時（プロキシ生成時の解析）。PropertyReferenceException で起動失敗。実行時まで待たない（fail-fast）。

Q4. メソッド名に書くのはフィールド名(camelCase)？ DB列名(snake_case)？

Entityのフィールド名(camelCase)。ObservationPoint → observationPoint、MeasuredAt → measuredAt。DB列名ではない。

Q5. save() 1回はトランザクションになっている？

なっている。SimpleJpaRepository のメソッドに @Transactional が付いているため。複数操作を束ねたいときはService側に @Transactional を付ける。

11. 次にやること

🟣 Repositoryの仕組みが分かったら、次は外部API（ポールンロボ）→ DTO → Entity → Repository.save() の流れを作ります。save() が裏でどんなSQLを出すか、spring.jpa.show-sql をONにして観察しながら進めると理解が深まります。
そして「Repositoryが実際にDBへ書けるか」は、Docker Compose で PostgreSQL を起動して初めて確認できます（コンパイル成功≠DB疎通成功）。
🟢 Phase 4への伏線：今は「Springの便利機能」として使ったが、DDDでは Repository は「集約の永続化を隠す境界」になる。今の ObservationPointRepository が、その「ドメインとDBの境界線」の原型。プロキシという実装詳細をドメインから完全に隠せている点が、まさにDDDが目指す形。
