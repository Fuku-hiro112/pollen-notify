🐳 DB接続＆起動検証プラン

花粉通知アプリ ／ 2026-06-01 ／ Phase 1 ／ Docker + Flyway + Hibernate validate

このプランのゴール
ここまで「コンパイルは通った」状態でしたが、コンパイル成功＝DBで動く、ではありません。PostgreSQL を起動し、アプリを起動して、次の2つを実DBで検証します：
  1. Flyway が V1__init.sql を流してテーブルが作られる
  2. Hibernate の ddl-auto: validate が「Entityのマッピング ↔ 実テーブル」の一致を検証してパスする
これが通れば、B方針で書いた @Column 制約・@SequenceGenerator・複合UNIQUE が本当に正しかったと証明できます。

1. 全体の流れ

docker compose up -d      ← ① PostgreSQL コンテナ起動
        │
        ▼
./gradlew bootRun         ← ② アプリ起動
        │
        ├─ Flyway が V1__init.sql を実行 → テーブル作成
        └─ Hibernate validate が Entity ↔ テーブル を照合
        │
        ▼
  起動成功 = 検証パス 🎉
🔵 前提（すでに用意済み）：docker-compose.yml（PostgreSQL 16）・application.yml（validate + Flyway + show-sql）・.env（接続情報）・依存（postgresql / flyway / webmvc）はすべて投入済み。新しく書くものはありません。起動して確認するだけ。

2. Step 1: PostgreSQL を起動

プロジェクトのルート（docker-compose.yml がある場所）で実行します。IntelliJ の内蔵ターミナル（Alt+F12）でOK。

  • ターミナルをプロジェクトルートで開く（docker-compose.yml が見える場所）
  • docker compose up -d を実行（-d はバックグラウンド起動）
  • docker compose ps で pollen-notify-db が healthy になるのを確認（数秒かかる）
🔵 コマンド 
# 起動
docker compose up -d

# 状態確認（STATUS が "healthy" になればOK）
docker compose ps
🟣 healthcheck（pg_isready）が docker-compose.yml に仕込んであるので、healthy 表示まで待てば「DBが接続を受け付ける状態」が保証されます。healthy 前にアプリを起動すると接続エラーになることがあるので、ひと呼吸待つ。

3. Step 2: アプリを起動して検証

  • DBが healthy なのを確認済み
  • ./gradlew bootRun でアプリ起動（IntelliJなら起動構成の ▶ でも可）
  • ログに Flyway ... Successfully applied 1 migration 系が出る
  • ログに Started PollenNotifyApplication in X.XXX seconds が出る（=起動成功）
  • エラーで落ちていない（SchemaManagementException 等が無い）
  • 確認できたら Ctrl+C でアプリ停止
🔵 コマンド 
./gradlew bootRun
# Windows PowerShell でも同じ。IntelliJ内蔵ターミナル推奨

4. 起動ログの読み方（成功 / 失敗）

✅ 成功パターン（こう出れば検証パス）

Flyway Community Edition ... by Redgate
Successfully validated 1 migration
Migrating schema "public" to version "1 - init"
Successfully applied 1 migration to schema "public"
...
Started PollenNotifyApplication in 3.2 seconds
🟢 ここまで出れば、Flyway がテーブルを作り、Hibernate validate が Entity と一致を確認して起動完了。あなたのEntity設計が実DBで正しいと証明された。

🔴 失敗パターン例：validate でマッピング不一致

org.hibernate.tool.schema.spi.SchemaManagementException:
  Schema-validation: missing column [xxx] in table [yyy]
🔴 これは「Entityが期待する列が実テーブルに無い」＝マッピングとDDLのズレ。例：@Column(name=...) の綴り間違い、フィールドを追加したのにDDL未更新、など。エラーにテーブル名・列名が出るので、その列をSQLとEntityで突き合わせる。

🔴 失敗パターン例：DBに繋がらない

org.postgresql.util.PSQLException: Connection refused / FATAL: password authentication failed
🔴 DB未起動、.env の値とDBの不一致、ポート競合など。→ トラブルシュート参照。
📚 関連：Spring Data JPA 内部の仕組み（show-sql でSQLを観察）／ 命名規則（列名ズレの原因切り分け）

5. Step 3: テーブルを直接のぞく（任意）

本当にテーブルができたか、自分の目で確認すると納得感があります。

  • docker compose exec db psql -U <ユーザー> -d <DB名> で psql に入る（.env の値を使う）
  • \dt で observation_points / pollen_measurements / flyway_schema_history が見える
  • \d observation_points で列・制約（NOT NULL / UNIQUE）がDDLどおりか確認
  • \q で抜ける
🟣 flyway_schema_history という表が自動で出来ています。これはFlywayが「どのマイグレーションを適用済みか」を記録する管理表。次に V2__... を足すと差分だけ適用される仕組みの正体。

7. 理解度チェック

Q1. ddl-auto: validate は何をする設定？ create と何が違う？

validate=「Entityと既存テーブルが一致するか検証だけ」。create=「Hibernateがテーブルを作り直す」。本プロジェクトはFlywayがDDL担当なので、Hibernateは検証のみ＝validate。

Q2. アプリが起動成功した、ということは何が保証された？

① FlywayがV1を適用しテーブルが出来た ② Entityのマッピングが実テーブルと一致した（validateパス）。つまりEntity設計が実DBで正しい。

Q3. flyway_schema_history 表の役割は？

適用済みマイグレーションの記録。次に V2 を追加したとき、未適用の差分だけを順に当てるための台帳。

Q4. show-sql: true にしていると何が見える？ なぜ今ONにしている？

HibernateがDBへ発行する実SQL。学習中は「自分のコードがどんなSQLになるか」を観察できるのでON。本番は大量ログになるのでOFFにする。

🟢 このプランがすべて ✅ になったら、Phase 1 の「器」が完成です（Entity・Repository・DBが実際に繋がった状態）。
