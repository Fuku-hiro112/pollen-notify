3. Step 1: Client（RestClientでCSVを取得）

📁 ファイル：src/main/java/com/fuku/pollen_notify/client/PollenApiClient.java（client パッケージを新規作成）

RestClient を使います（モダンな同期HTTPクライアント。古い教材の RestTemplate ではなくこちら）。今回はレスポンスをCSV文字列（String）そのまま受け取ります（パースは次のステップ）。

🔵 形（穴埋めしてください） 
@Component
public class PollenApiClient {

    private final RestClient restClient;

    // base-url を注入して RestClient を組み立てる（@Value か設定クラス。後述）
    public PollenApiClient(@Value("${pollen-api.base-url}") String baseUrl) {
        this.restClient = RestClient.create(baseUrl);
    }

    /** citycode を指定して CSV 文字列を取得する */
    public String fetchRawCsv(String cityCode) {
        return restClient.get()
                .uri(uriBuilder -> uriBuilder.queryParam("citycode", ___).build())
                .retrieve()
                .body(String.class);   // ← CSVをそのまま文字列で受ける
    }
}
🟡 @Component を付けてSpringのBeanにする（DIで Service に注入するため）。RestClient の生成はコンストラクタで1回だけ（毎回作らない）。
📚 公式：Spring RestClient

4. Step 2: DTO（CSV1行を表す入れ物）

📁 ファイル：src/main/java/com/fuku/pollen_notify/dto/PollenCsvRow.java（dto パッケージを新規作成。Javaの record として作る）

🟢 DTO は「APIの形」をそのまま写した入れ物。Entityとは別物にするのが鉄則：APIの都合（CSVの列）とDBの都合（テーブル）を分離するため。APIが変わってもEntityを守れる。
🖊️ あなたの作業：Step 0 で見た列に合わせて DTO を作る。Java の record が最適（不変・簡潔）。 
// 例（実際の列はStep 0の観察に合わせる）
public record PollenCsvRow(
        String cityCode,
        Instant measuredAt,
        int pollenCount
) {}
🟣 なぜ record か：DTOは「運ぶだけ」で振る舞いを持たない。record なら getter・equals・toString が自動で、不変（変更不可）。Phase 4でも値オブジェクトの足がかりになる考え方。

5. Step 3: CSVをパースしてDTOにする

📁 ファイル：client/PollenApiClient.java 内のメソッドとして書く（Step 1 と同じファイル）。Client が「CSVを取得し、List<PollenCsvRow> として返す窓口」になる。
※ Phase 1はこれで十分。将来パースが複雑化したら client/PollenCsvParser.java に切り出す。

取得したCSV文字列を Apache Commons CSV で1行ずつDTOに変換します（手で split(",") しない：引用符やカンマ混入で壊れるため）。

🔵 形（骨格） 
// CSV文字列 → List<PollenCsvRow>
List<PollenCsvRow> parse(String csv) throws IOException {
    CSVFormat format = CSVFormat.DEFAULT.builder()
            .setHeader()              // 1行目をヘッダとして扱う（Step 0で確認した形に合わせる）
            .setSkipHeaderRecord(true)
            .build();

    try (CSVParser parser = CSVParser.parse(csv, format)) {
        List<PollenCsvRow> rows = new ArrayList<>();
        for (CSVRecord record : parser) {
            String cityCode = record.get("___");        // 列名 or インデックス
            int count       = Integer.parseInt(record.get("___"));
            Instant at      = /* 日時文字列をInstantへ変換（DateTimeFormatter） */;
            rows.add(new PollenCsvRow(cityCode, at, count));
        }
        return rows;
    }
}
🟡 日時のパースは詰まりやすい。CSVの文字列（例 2026-03-01 09:00:00）にはタイムゾーン情報が無いことが多い。「これは日本時間(JST)」と解釈して Instant（UTC基準）へ変換する必要がある。LocalDateTime.parse(...).atZone(ZoneId.of("Asia/Tokyo")).toInstant() のような流れ。application.yml で time_zone: UTC にしてあるのと整合させる。

6. Step 4: DTO → Entity 変換（-9999の判断）

📁 ファイル：service/PollenIngestService.java 内のメソッドとして書く（地点解決に Repository が要るため、Service内が自然）。専用クラスに分けるのは Phase 4 で検討。

ここがドメインの核。前に作った静的ファクトリ PollenMeasurement.of(...) を使います。そしてここで -9999＝欠測の判断を入れます（以前話した「API解析層で弾く」がここ）。

🖊️ あなたが考えること
  • -9999（欠測）の行は、PollenMeasurement を作らずスキップする（保存しない）。of() の負数ガードに到達する前に、ここで除外するのが筋。
  • of() は ObservationPoint を要求する。CSVには cityCode(=external_id) しかない。地点をどう用意する？ → observationPointRepository.findByExternalId(cityCode) で取得（無ければ新規作成して保存）。ここで前に作ったメソッドが活きる！
🔵 変換メソッドの命名：DTO（別の型）から作るので、命名規則ガイドのとおり from が自然。 
// 例：マッパー的なメソッド
PollenMeasurement toEntity(PollenCsvRow row, ObservationPoint point) {
    return PollenMeasurement.of(point, row.measuredAt(), row.pollenCount());
}
// 欠測(-9999)行は、ここを呼ぶ前にフィルタで除外する

7. Step 5: Service（全体を束ねる）

📁 ファイル：src/main/java/com/fuku/pollen_notify/service/PollenIngestService.java（service パッケージを新規作成）

Client・変換・Repository を組み合わせ、「取得 → パース → 欠測除外 → 地点解決 → 重複チェック → 保存」を1つの流れにします。

🔵 骨格（流れの設計図） 
@Service

    private final PollenApiClient client;

    private final PollenMeasurementRepository measurementRepo;

                               PollenMeasurementRepository measurementRepo) { ... }

        String csv = client.fetchRawCsv(cityCode);
        List<PollenCsvRow> rows = parse(csv);

        // 1. 地点を解決（無ければ作る）
        ObservationPoint point = pointRepo.findByExternalId(cityCode)
                .orElseGet(() -> /* 新規作成して save */ );

        for (PollenCsvRow row : rows) {

            // 3. 重複チェック：existsByObservationPointAndMeasuredAt
            // 4. PollenMeasurement.of(...) を save
        }
    }
}
🟢 @Transactional をServiceに付ける意味：複数行の保存を「全部成功か全部失敗」の1単位にする。前の「内部の仕組み」HTMLで触れた、Repository単体トランザクションをService側で束ねるケースがこれ。
🟣 重複防止の合わせ技：保存前に existsByObservationPointAndMeasuredAt でチェック（アプリ側）＋ DBの複合UNIQUE制約（最後の砦）。二重で守るのが堅牢な設計。前に作った両方がここで噛み合う。

9. やりがちな失敗

🔴 DTOを使わずEntityに直接APIをマッピング：APIの形がEntityに侵食し、API変更でEntity（とDB）が巻き込まれる。必ずDTOで分離。
🔴 split(",") で手パース：値中のカンマや引用符で壊れる。Commons CSV を使う。
🟡 日時をタイムゾーン無視で変換：JSTのつもりがUTCで保存され9時間ズレる。ZoneId を明示。
🟡 欠測(-9999)をそのまま保存しようとして例外：of() の負数ガードで落ちる。保存対象を作る前にスキップするのが正しい流れ。

10. 理解度チェック

Q1. なぜ DTO と Entity を分けるのか？

APIの都合（CSVの列構成）とDBの都合（テーブル設計）を分離するため。APIが変わってもEntity/DBを守れる。混ぜるとAPI変更がDBまで波及する。

Q2. -9999（欠測）はどこで弾くのが正しい？ なぜ of() のガードだけではダメ？

API解析層（変換前）でスキップするのが正しい。of() のガードは「不正値の観測を作らせない最後の砦」。欠測は"作るべきでないもの"なので、of() を呼ぶ前に除外する。ガードに頼ると例外で流れが止まる。

Q3. CSVの cityCode から ObservationPoint をどう手に入れる？ 前に作った何が役立つ？

observationPointRepository.findByExternalId(cityCode)。無ければ新規作成して保存。前に書いた派生クエリメソッドがここで活きる。

Q4. Service に @Transactional を付ける理由は？

複数行の保存を1つのトランザクション（全部成功 or 全部失敗）に束ねるため。Repository単体のトランザクションをService側でまとめるケース。

Q5. 重複保存を防ぐ二重の仕組みは？

① アプリ側：existsByObservationPointAndMeasuredAt で保存前チェック ② DB側：複合UNIQUE制約。両方で守る。
