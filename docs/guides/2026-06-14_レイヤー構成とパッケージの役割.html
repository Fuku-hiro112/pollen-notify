1. そもそも「レイヤー」とは？なぜ分けるのか

レイヤードアーキテクチャ とは、プログラムを「役割の違う層」に分ける考え方です。料理屋に例えると：

役割料理屋での例えこのアプリ
外部から材料を取る市場へ買い出しに行く人client
運ぶ箱食材を入れるトレーdto
調理手順を仕切る料理長service
保存する形冷蔵庫の保存容器entity
冷蔵庫に出し入れ倉庫係repository
🟡 なぜ分けるのか（混ぜると何が困る？） 全部を1つのクラスに書くと、「APIの仕様変更」「DBの設計変更」「業務ルールの変更」が すべて同じ場所に絡まり、1か所直すと別の機能が壊れます。 役割で分ければ「変更したい理由ごとに、触る場所が1か所で済む」——これが分割の最大の利点です。

2. 全体像 — データの流れ（図解）

Phase 1 の「花粉データを取得してDBに保存する」処理は、各レイヤーをバケツリレーのように通ります。

左から右へ：API → client が取得 → dto に詰める → service が変換を仕切る → entity の形にする → repository が DB へ保存。 各箱が「自分の担当だけ」やり、隣に渡すのがポイントです。

3. client — 外部との境界

🟢 役割 外部システム（他社のAPIなど）とやり取りする係。「外の世界」と「自分のアプリ」の境界に立ち、 通信の詳細（URL・HTTP・レスポンス形式）をここに閉じ込めます。

あなたの PollenApiClient：

public String fetchRawCsv(String cityCode) {
    return restClient.get()
            .uri(b -> b.queryParam("citycode", cityCode).build())
            .retrieve()
            .body(String.class);   // CSVをそのまま文字列で受ける
}

RestClient を使い、APIから CSV を「文字列のまま」取ってくるのが client の仕事。パースも保存もしません （それは別レイヤーの担当）。「取ってくるだけ」に徹しているのが正しい姿です。

🟣 学習Tips client を分けておくと、将来APIが別会社のものに変わっても「client だけ差し替えれば」他の層は無傷で済みます。

4. dto — 層をまたぐ入れ物

🟢 役割 DTO ＝「データを運ぶための箱」。ロジックを持たず、ただ値を保持して層から層へ受け渡します。

あなたの PollenCsvRow：

public record PollenCsvRow(
        String cityCode,
        Instant date,
        int pollen_count
) {}

Java の record で書かれています。CSV 1行ぶんの生データを、client → service へ運ぶための箱です。

🟡 なぜ entity と分けるのか？ 「APIのCSV形式」と「DBのテーブル形式」は別物で、別々の理由で変わるからです。 dto は「外から来たデータの形」、entity は「DBに保存する形」。混ぜると、API変更がDB設計に波及してしまいます。

5. service — 業務手順の司令塔

🟢 役割 「やりたいこと」の手順をまとめる司令塔。client・repository などの部品を呼び出して、 1つの業務（例：取得→変換→保存）を組み立てます。業務ルールもここに置きます。

あなたの PollenIngestService（現状は変換メソッドのみ）：

PollenMeasurement toEntity(PollenCsvRow row, ObservationPoint point) {
    return PollenMeasurement.of(point, row.measuredAt(), row.pollenCount());
}
// 欠測(-9999)行は、ここを呼ぶ前にフィルタで除外する

ここでは dto（PollenCsvRow）を entity（PollenMeasurement）に変換しています。 「欠測行を除外する」といった業務ルールも service の担当です。

🖊️ ここはあなたが育てる場所 Phase 1 の残り「取得→パース→保存を1本につなぐ」処理は、まさにこの service に書きます。 client.fetchRawCsv() → parse() → toEntity() → repository.save() の流れを組み立てるのが次の課題です。

6. entity — DBの1行に対応

🟢 役割 Entity ＝DBテーブルの1行に対応するクラス。 ORM の仕組みで、Javaオブジェクトとテーブル行が自動で行き来します。

あなたの PollenMeasurement（抜粋）：

@Entity
@Table(name = "pollen_measurements", uniqueConstraints = ...)
public class PollenMeasurement {
    @Id @GeneratedValue(...) private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "observation_point_id")
    private ObservationPoint observationPoint;

    @Column(name = "measured_at") private Instant measuredAt;
    @Column(name = "pollen_count") private int pollenCount;
}

主なアノテーション（ホバーで説明）：

  • @Entity … テーブル対応クラスの宣言
  • @Id … 主キー
  • @ManyToOne … 観測値（多）→観測地点（一）の関連
  • FetchType.LAZY … 必要になるまで観測地点を読まない
  • @Column … 列への対応
🟣 設計の芽 あなたの entity は of(...) という生成メソッドで「count < 0 なら例外」という ルールを持っています。これは「データに振る舞いを持たせる」DDDの第一歩です（→ 10章）。

7. repository — DBアクセス係

🟢 役割 DBへの保存・検索を担当する係。「SQLを書く場所」をここに集約します。 Spring Data JPA を使うと、インターフェースを書くだけで実装が自動生成されます。

あなたの PollenMeasurementRepository：

public interface PollenMeasurementRepository
        extends JpaRepository<PollenMeasurement, Long> {
    boolean existsByObservationPointAndMeasuredAt(ObservationPoint point, Instant measuredAt);
}

JpaRepository を継承するだけで save() や findById() が使えます。さらに、 existsByObservationPointAndMeasuredAt のように メソッド名規約 で書くと、その名前から SQL を自動生成してくれます（重複保存チェックに使えます）。

🟡 ポイント 「実装クラスが見当たらない！」と戸惑いますが、それで正常です。実体はSpringが起動時に裏で作っています。

8. 責務の対比表

レイヤーやることやらないこと
client外部APIを呼んで生データを取るパース・保存・業務判断
dtoデータを保持して運ぶロジック・DB保存
service手順の組み立て・変換・業務ルールHTTP通信の詳細・SQLの詳細
entityDB1行を表す・自身の整合性を守るAPI通信・他テーブルの一括検索
repository保存・検索（DBアクセス）業務ルールの判断

9. 初学者がやりがちな混同

🔴 やりがちな失敗
  • entity を外部にそのまま返す：API のレスポンスに entity を直接使うと、DB構造が外部に漏れ、変更に弱くなる。→ 返却用 dto を別途用意する（Phase 3）。
  • service に SQL を直書き：DBアクセスは repository の担当。service が SQL を持つと役割が崩れる。
  • client にパース処理を詰め込む：client は「取ってくるだけ」。パースは service 寄り（あなたの parse は client 内にあるが、Phase 4 で整理候補）。
  • controller を作って全部そこに書く：1クラス肥大化の典型。レイヤーに散らす。

10. 🟣 Phase 4 への伏線（DDD）

今のレイヤー構成は「データの流れで分ける」考え方です。Phase 4 の DDD では、これを「業務の概念で分ける」方向へ進化させます：
  • entity に振る舞いを増やす：今の PollenMeasurement.of() の検証がさらに育つ
  • 値オブジェクト：pollenCount をただの int でなく「花粉数」という型に
  • 集約：観測地点と観測値のまとまりを設計し直す
今は「動く貧弱なコード」を完成させるのが最優先。今日の構成理解が Phase 4 の土台になります。

11. 理解度チェック

Q1. client の役割を一言で？

外部API（外の世界）とやり取りして生データを取ってくる係。パースや保存はしない。

Q2. dto と entity を分けるのはなぜ？

「APIのデータ形式」と「DBのテーブル形式」は別物で、別々の理由で変わるから。混ぜると変更が波及する。

Q3. repository の実装クラスはどこにある？

自分で書かない。Spring Data JPA がインターフェースから起動時に自動生成する。

Q4. 「取得→変換→保存」の手順を組み立てるのはどのレイヤー？

service。部品（client・repository）を呼び出して1つの業務にまとめる司令塔。

Q5. entity を API のレスポンスにそのまま使うと何が問題？

DBの内部構造が外部に漏れ、テーブル変更がAPIに直撃する。返却用のdtoを別に用意すべき。

12. 次にやること

🔵 次の一歩（Phase 1 の残り） このレイヤー理解を踏まえ、service で「取得→パース→保存」を1本につなぐのが次の課題です：
  1. PollenApiClient.fetchRawCsv() で CSV取得
  2. parse() で List<PollenCsvRow> に変換
  3. 各 row を toEntity() で PollenMeasurement に変換（欠測は除外）
  4. repository.save() で保存（重複は existsBy... でスキップ）
  5. 実際に1回動かして、DBに行が入るのを確認 → Phase 1 クリア
