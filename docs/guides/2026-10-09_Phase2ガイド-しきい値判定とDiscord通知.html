1. 全体像と、なぜこの順番か

Phase 2 のゴールは「花粉観測値がしきい値を超えたら、Discordに通知が届く」。やることは3つですが、 作る順番が学習効率を大きく左右します。

🟢 なぜ「自動化（H）」を最後に回すのか @Scheduled（定期実行）を先に作ると、1時間ごと・1日ごとに自動実行されるため、 動作確認のたびに長時間待つか、時間を無理やり早回しする工夫が必要になります。

たとえるなら「炊飯器の味を確認したいとき、まず鍋で1杯だけ試し炊きする」のと同じです。 炊飯器（自動化）にセットして炊き上がりを待つより、鍋（手動実行）で先に味（ロジック）を確かめる方が早い。 IngestRunner（起動時に1回だけ実行）は、すでにその「試し炊き用の鍋」として使えます。
🔵 だからこの順番
  1. F：しきい値判定 — 外部依存ゼロの純粋なロジック。一番安全に・一番速く試行錯誤できる
  2. G：Discord通知 — Fの判定結果を実際に送る。ここで初めて外部サービス（Discord）と繋がる
  3. H：定期実行化 — F・Gが動くと分かってから、最後に自動化のフタを閉める

2. F課題F：しきい値判定ロジック

🟢 やさしく説明：通知判定とは 通知判定（Notification Decision） ＝「この花粉の量は、知らせるべき量か？」を判断する役。たとえるなら体温計の『発熱ライン』判定です。 体温計自体は「36.2℃」という値を測るだけ（＝Phase 1のpollen_count）。 「37.5℃を超えたら発熱」というライン（しきい値）と比べて初めて「これは通知すべき状態だ」と判断できます。
体温計の世界このアプリの世界
36.2℃（測った値）pollen_count（観測値）
37.5℃（発熱ライン）しきい値
「発熱している」という判断NotificationDecision の判定結果
🖊️ あなたが決める（設計判断①：しきい値をどこに置くか） 本来は「通知設定（Notification Preference）」としてユーザーごとにDB管理すべきですが、それは プロジェクトのCLAUDE.mdのフェーズ表で Phase 3（REST APIで設定管理）の担当です。 Phase 2 ではまだそこに踏み込まず、固定値（定数）でよい、というのが推奨です。
  • 固定値にする理由を自分の言葉で説明できますか？（ヒント：「今作っていないものを先取りで作らない」というシンプルさの原則）
🟢 実在の基準を調べて決めた（2026-10-10、Claudeが検索して確認） 日本気象協会の花粉飛散予報では、以下の4段階が使われています。
値予報表現
0〜少ないでしょう
10〜やや多いでしょう
30〜多いでしょう
50以上非常に多いでしょう

出典：ウェザーニューズ「全国の花粉飛散数のリアルタイムデータを無料で公開」内の日本気象協会基準の紹介

🟡 未確認・注意点（API仕様メモにも記録済み） この基準は本来1日の合計値に対するものですが、私たちのAPIが返すのは1時間ごとの値です。 さらに、ポールンロボ本体の単位は検索結果だと個/cm²とされており、私たちの API仕様メモに書いた「個/m³」と食い違っています（API自体に単位の明記はなし）。 厳密な裏付けはまだ無い前提で、「仮の目安」として採用します。Phase 3で設定を調整可能にする時に見直す候補です。
🟢 決定：THRESHOLD = 10、ただし「段階」で持つ しきい値ちょうど（10）が「やや多い」の境目に一致するため、boolean（超えた/超えてない）だけでなく、 4段階そのものを表す型を作る方が、後で通知文面に「やや多いでしょう」のような表現を使えて一石二鳥です。 enum を使うとこう書けます。

3. G課題G：通知ポート抽象化 + Discord通知

🟢 やさしく説明：なぜ「抽象化」するのか CLAUDE.mdのPhase 2の学習対象に「通知ポート抽象化」とあります。これは 「通知の送り先（Discord）を、後で差し替えられる形にしておく」という考え方です。

たとえるなら電源プラグの規格です。家電（判定ロジック）は「コンセントに挿せば電気が流れる」ことだけ知っていればよく、 電気が火力発電か太陽光かは気にしません。将来LINE通知（Phase 5で任意拡張とCLAUDE.mdに記載あり）を追加する時、 「コンセント（インターフェース）」さえ合っていれば、家電側（判定ロジック）を一切変えずに済みます。
🔵 具体的には：インターフェース1つ + 実装1つ 
public interface NotificationSender {
    void send(String message);
}
@Component
public class DiscordNotificationSender implements NotificationSender {

    private final RestClient restClient;

    public DiscordNotificationSender(@Value("${discord.webhook-url}") String webhookUrl) {
        this.restClient = RestClient.create(webhookUrl);
    }

    @Override
    public void send(String message) {
        restClient.post()
                .contentType(MediaType.APPLICATION_JSON)
                .body(/* ★ Discord Webhookが期待するJSONの形を作る */)
                .retrieve()
                .toBodilessEntity();
    }
}

4. H課題H：@Scheduled で定期実行化

🟢 やさしく説明：@Scheduled とは CommandLineRunnerは「開店と同時に1回だけ流れるアナウンス」でした。 @Scheduledはその進化版で、 「毎日・毎時間、決まった時刻に繰り返しアナウンスする」仕組みです。
🔵 必要なこと
  1. メイン設定クラス（PollenNotifyApplication）か、別の設定クラスに @EnableScheduling を付ける
  2. 定期実行したい処理に @Scheduled(...) を付ける
@Component
public class PollenNotificationScheduler {

    private final PollenIngestService ingestService;
    private final NotificationDecision decision;
    private final NotificationSender sender;
    // ...コンストラクタで注入...

    @Scheduled(/* ★ cron か fixedRate、どちらでいつ実行する？ */)
    public void run() {
        /* ★ ingest → 最新の観測値を取得 → 判定 → 通知、の流れ */
    }
}
🖊️ あなたが決める（設計判断③：いつ実行する？）
方式意味向いている場面
fixedRate前回の開始から○ミリ秒後に次を実行「とにかく一定間隔で」。時刻は気にしない処理
cron「毎日7時」のように具体的な時刻を指定人の生活リズムに合わせたい処理
ポールンロボAPI仕様メモによれば、花粉データは1時間おきに更新されます。 「毎朝〇時に、花粉の心配をしたい人に知らせる」という本来の目的を考えると、fixedRateで数秒おきに叩くのは APIへの負荷的にも目的的にも不向きです。cronで「1日1回・朝の決まった時刻」が自然ではないか、考えてみてください。
🟡 設計判断④：IngestRunner はどうする？ IngestRunner（起動時1回）を削除して@Scheduledに一本化するか、 開発中の手動確認用として残すかは選べます。削除する場合、§5の動作確認は @Scheduled の実行時刻を待つ必要がある点に注意。
  • @EnableScheduling を付けた
  • cron か fixedRate を選び、理由を言葉にできる
  • PollenNotificationScheduler（名前は自由）を作り、ingest→判定→通知の流れを書いた
  • IngestRunner を残すか消すか決めた

5. I課題I：動かして確認

🔵 確認すべき2つのケース しきい値判定は「境界」がある処理なので、両方のケースを確認しないと「たまたま動いた」で終わってしまいます。
  • しきい値を超えるデータで実行し、Discordに通知が届くのを目で見る
  • しきい値を超えないデータで実行し、Discordに何も届かないことを確認する
  • ちょうどしきい値と同じ値のケースで、§2で決めた境界の挙動（通知する/しない）通りになっているか確認する
  • （@Scheduledを使う場合）指定した時刻・間隔で実際に動くのを確認する
🟣 テスト用データの作り方のヒント Phase 1で確認した通り、花粉の観測期間外は404になります。しきい値を超える値を確実に用意したい場合、 APIの実レスポンス例にある観測期間内の日付（例：花粉が多い3月）を使うか、 あるいは判定ロジック（F）だけを単体で動かして固定の数値（例：decision.shouldNotify(999)）で試すと、APIの季節に振り回されずに確認できます。

6. やりがちな失敗

  • しきい値の境界を逆に書く → > と >= を取り違えて、ちょうどの値で通知する/しないが意図と逆になる
  • Webhook URLをコードに直書き・Gitにコミット → 誰でもそのチャンネルに投稿できる状態になる（§3）
  • @EnableScheduling を付け忘れる → @Scheduled を付けても何も起きない（エラーも出ないので気づきにくい）
  • fixedRateで短い間隔を指定 → 外部APIへの過剰なアクセスになる。Phase 1の404/400の仕様を思い出す
  • 通知ロジックとDiscord送信を1つのクラスに混ぜる → 後でLINE通知を追加する時、判定ロジックまで書き直すことになる（§3の抽象化の意味が消える）

7. 理解度チェック

Q1. しきい値をPhase 2では固定値にする理由は？

ユーザーごとの通知設定（Notification Preference）のDB管理はPhase 3の担当。今作っていない機能を先取りして作らない、というシンプルさの原則。

Q2. NotificationSender をインターフェースにする理由は？

通知の送り先（Discord/LINE等）を差し替え可能にするため。判定ロジック側は送信手段の詳細を知らなくてよくなる（通知ポート抽象化）。

Q3. cron と fixedRate の使い分けは？

fixedRateは一定間隔、cronは具体的な時刻指定。人の生活リズムに合わせる通知ならcronが自然。

Q4. @Scheduled を付けても動かない時、まず疑うべきことは？

@EnableScheduling が付いているか。付け忘れてもコンパイルエラーにならないため気づきにくい。

Q5. なぜF（判定ロジック）から作り、H（定期実行）を最後にするのか？

定期実行を先に作ると、動作確認のたびに実行時刻を待つ必要がある。外部依存のない純粋なロジックから作ることで、速く・安全に試行錯誤できる。
