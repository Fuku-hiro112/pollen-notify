3. A課題A：createdAt を自動設定（@PrePersist）

✅ この課題は完了しています（2026-08-27 確認） PollenMeasurement.java:43-46 に @PrePersist void onCreate() が実装済みです。 以下は「なぜそうしたか」を思い出すための記録として残しています。

そもそも何が問題だったのか（やさしく説明）

createdAt とは、花粉観測値が持つ項目のひとつで「このデータをいつ保存したか」という日時を入れる場所です。 コードではこう書かれています： 

@Column(nullable = false)
private Instant createdAt;

この nullable = false がポイントです。

  • null（ヌル）＝「何も入っていない・空っぽ」という状態
  • nullable = false＝「この項目は空っぽのままにしてはダメ」というデータベース側のルール
🟢 例えるなら「必須入力の申込書」 役所の申込書で「氏名（必須）」を空欄のまま出すと、窓口で突き返されますよね。それと全く同じです。
申込書の世界このアプリの世界
「氏名（必須）」の欄nullable=false の createdAt
空欄のまま提出createdAt を空っぽのまま保存しようとする
窓口で突き返されるデータベースがルール違反としてエラーを出す
🔴 直す前は、なぜ「落ちる」状態だったのか データを作る of() メソッドは observationPoint・measuredAt・pollenCount は入れるのに、 createdAt は入れません。そのまま保存すると：
  1. of() でオブジェクトを作る → createdAt は空っぽ
  2. データベースに保存しようとする
  3. DBが「createdAt は空欄禁止のはずだ！」と拒否
  4. エラーで保存が失敗する（＝申込書を突き返された状態）
これが NOT NULL 制約違反で 例外になる、の正体です。

どう直したか

「保存する直前に、createdAt へ自動で現在時刻を入れる」仕組みを足しました。JPA らしいのは @PrePersist です。 

@PrePersist
void onCreate() {
    this.createdAt = Instant.now();
}
  • @PrePersist のメソッドを PollenMeasurement に追加した
  • 「なぜ生成時ではなく保存時に入れるのか」を自分の言葉で説明できる
🟣 別解（知識として） Hibernate の @CreationTimestamp を使う手もあります。ただし「JPA標準ではなくHibernate独自」。 今は標準の @PrePersist で十分です。

4. B課題B：@Transactional をどこに付けるか

🟡 現状（2026-08-27 確認） ingest() に @Transactional は付いています。ただし import が jakarta.transaction.Transactional です。動きはしますが、Spring では org.springframework.transaction.annotation.Transactional が標準（ロールバック対象の例外の扱いなどが微妙に違う）。ここだけ差し替えてください。
🟢 トランザクションとは（やさしく説明） トランザクション ＝「いくつかの作業をまとめて1つの塊として扱い、途中で失敗したら全部なかったことにする」仕組みです。

例えるなら銀行の送金。「Aから引く」「Bに足す」の2つは、両方成功して初めて意味があります。 もし「Aから引いた直後に停電」で片方だけ実行されたら大問題ですよね。だから 「両方成功 or 両方取り消し（＝ロールバック）」にまとめます。

このアプリでは ingest() が「たくさんの観測値をまとめて保存する」作業です。 10件保存中に5件目でエラーが出たとき、「4件だけ入って残りは無い」という中途半端な状態は避けたい。 だから ingest() 全体を1つの塊にします。

🖊️ あなたが直す（import の1行だけ） 
- import jakarta.transaction.Transactional;
+ import org.springframework.transaction.annotation.Transactional;
  • ingest() に @Transactional を付けた
  • import を org.springframework.transaction.annotation.Transactional に変更した
  • ./gradlew compileJava が通ることを確認した

5. C課題C：重複保存を防ぐ（existsBy）

同じ処理を2回動かすと、まったく同じ観測値（同じ地点・同じ時刻）が2件ダブって保存されます。これを防ぎます。

🟢 やさしく説明 repository（DBアクセス係）には existsByObservationPointAndMeasuredAt(point, measuredAt) というメソッドがあります。 これは「その地点・その時刻のデータは、もうDBに有る？」を尋ねて 有る＝true / 無い＝false を返します。これを使って「まだ無いデータだけ保存する」ようにします。
🖊️ あなたが書く（どこに足すか考える） 
List<PollenMeasurement> entities = rows.stream()
        .filter(this::isValid)
        .filter(row -> /* ★ まだ保存されていない行だけ通す条件 */)
        .map(row -> toEntity(row, point))
        .toList();
ヒント：existsBy... は「ある＝true」を返します。残したいのは「まだ無い行」なので、 条件をどう書く？（isValid の filter と同じ考え方）
  • filter を1つ追加して、既に保存済みの行を除外した
  • 条件の向き（true/false のどちらを残すか）を口で説明できる
  • アプリを2回起動しても行数が増えないことを SELECT count(*) で確認した
🟡 性能の小話（今は気にしなくてOK） この方式は行ごとに1回SQLを投げます（N回）。Phase 1 の少量データなら問題なし。 大量データでは「まとめて存在確認」に変える余地がある、と頭の片隅に。

6. D課題D：CommandLineRunner で起動時に実行

🟢 CommandLineRunner とは（やさしく説明） ingest() という「処理本体」はできました。でも誰かが呼ばないと動きません。 そこで「アプリが起動したら自動で ingest() を呼ぶ」係を作ります。それが CommandLineRunner です。

たとえるなら「店の開店と同時に1回だけ流す自動アナウンス」。アプリ起動（開店）が終わると、 run() に書いた処理（アナウンス）が自動で1回流れます。ボタンを押す手間なく確認できるので、Phase 1 の動作確認にぴったりです。

（補足： Bean という言葉が出てきますが、いまは「@Component を付けると Spring が自動で見つけて動かしてくれるクラス」くらいの理解でOKです）
🖊️ あなたが書く（新規クラス） 
@Component
public class IngestRunner implements CommandLineRunner {

    private final PollenIngestService service;

    public IngestRunner(PollenIngestService service) {   // 依存注入
        this.service = service;
    }

    @Override
    public void run(String... args) throws Exception {
        service.ingest(/* ★ 取得したい都市コード */);
    }
}
考える点：渡す cityCode は ポールンロボAPI仕様メモ の実在コードを使い、 かつ §2 の seed で observation_points に登録済みであること。
  • IngestRunner クラスを新規作成した（@Component + CommandLineRunner）
  • コンストラクタで PollenIngestService を受け取った（依存注入）
  • 渡す都市コードを決め、§2 の seed の external_id と一致させた

9. 理解度チェック

Q1. createdAt はなぜ @PrePersist で入れる？

DBのNOT NULL制約があり、保存直前に必ず値が必要だから。@PrePersist は INSERT 直前に自動で呼ばれるので入れ忘れを防げる。

Q2. @Transactional を ingest に付ける理由は？

複数行の保存を1単位にし、途中で失敗したら全部ロールバックして中途半端な状態を残さないため。

Q3. 重複を防ぐ filter の条件はどう書く？

existsBy...は「ある=true」。残したいのは「まだ無い行」なので否定（!）で「存在しない行だけ通す」。

Q4. CommandLineRunner は何のために使う？

アプリ起動完了直後に run() を1回実行させ、ingest を自動で呼ぶため（Phase 1 の手動確認用トリガー）。

Q5. 実行前に DB に用意しておくべきものは？

対象の観測地点（observation_points の行）。無いと findByExternalId が空で orElseThrow に落ちる。
